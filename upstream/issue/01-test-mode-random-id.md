# Offline test mode mints a random id on create, and the minted form differs between ports

Filed from [voxgig/likeness](https://github.com/voxgig/likeness), which builds one application in five languages against these SDKs and holds the ports to byte-identical output.

## What happens

When a `create` supplies no `id`, the `test` feature mints one at random. Two problems follow.

**It is not reproducible.** A test that creates a record gets a different id on every run, so nothing downstream of a create can be asserted on.

**The minted value is shaped differently in different languages.** TypeScript draws four values in `0..9999`, renders each as unpadded hex, concatenates, then pads the *whole string* to 16 characters. The other four render four full 16-bit values as `%04x`, giving exactly 16 characters with per-group padding.

| Port | File | Expression |
|---|---|---|
| TypeScript | `ts/src/feature/test/TestFeature.ts:256-259` | `((1e4 * Math.random() \| 0).toString(16) + …).padEnd(16, '0')` |
| Go | `go/feature/test_feature.go:220-222` | `fmt.Sprintf("%04x%04x%04x%04x", rand.Intn(0x10000), …)` |
| Python | `py/joplin_sdk/feature/test_feature.py:178-179` | `random.randint(0, 0xFFFF)` ×4 |
| Ruby | `rb/feature/test_feature.rb:154` | `"%04x%04x%04x%04x" % [rand(0x10000), …]` |
| C | `c/feature/test.c:245` | `snprintf(buf, …, "%04x%04x%04x%04x", …)` |

Even with an identical random stream the TypeScript output would not match the others. `Math.random() * 1e4` also covers only `0x0000`–`0x270F`, far less than the 16-bit range the other four draw from.

## Why it matters

likeness is a case study whose whole claim is that five generated ports produce identical bytes for identical input. A created record's id reaches stdout, so any test that creates a record cannot join the parity corpus. We now require an explicit id on every create — but that is a rule each consumer has to learn the hard way, and the divergence stays latent for anyone who does not.

## Reproduction

No credentials, no network.

```js
const { JoplinSDK } = require('@voxgig-sdk/joplin')  // or the local ts/dist build

const a = JoplinSDK.test({ entity: { note: {} } })
const b = JoplinSDK.test({ entity: { note: {} } })

console.log((await a.Note().create({ title: 'x' })).data().id)
console.log((await b.Note().create({ title: 'x' })).data().id)
// two different values, and different again on the next run
```

Observed, against `ts/dist` built from this revision:

```
minted id 1: "262924223437c100"
minted id 2: "1740130a1a0018b4"
explicit id : "n-explicit"
```

Note the trailing `00` on the first: that is `padEnd(16, '0')` filling for the unpadded groups, and it is the visible signature of the TypeScript spelling. An explicit id is honoured, which is the workaround.

Run the equivalent in `py/`, `rb/`, `go/` and `c/` and compare the shape of the minted ids.

## Suggested direction

1. **Make it deterministic** — a counter on the test feature's own per-client state would give reproducible ids at no cost; the mock already holds that state.
2. **Make it identical across ports** — one documented format. `%04x` four times is already the majority spelling; TypeScript is the outlier.

A third option worth weighing: refuse a create with no id in test mode, with an error saying to supply one. That turns a silent divergence into a message, which is how the rest of these SDKs behave.
