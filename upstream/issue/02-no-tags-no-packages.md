# No git tags and no published packages: the documented install path has nothing to install

## What happens

`README.md` offers, for each of the seven languages:

> publish pending — [install from git tag](https://github.com/voxgig-sdk/joplin-sdk/tags)

There are no tags.

```
$ git ls-remote --tags https://github.com/voxgig-sdk/joplin-sdk   # and the other three
(no output)

$ npm view @voxgig-sdk/joplin version
npm error code E404
```

Same for `@voxgig-sdk/obsidian`, `@voxgig-sdk/notion` and `@voxgig-sdk/linear`.

So the only way to depend on one of these SDKs today is a raw commit sha.

## Why it matters

likeness depends on four SDKs across five languages: twenty dependencies, every one of them currently a sha. That is workable — we pin by sha deliberately and record it in `spec/sources.aon` — but it has costs the project has to absorb:

- **A version number that pins nothing.** Every manifest says `0.0.1`. Two different trees are both `0.0.1`, so the declared version cannot appear in a lockfile, a bug report or a parity exception table and mean anything.
- **No upgrade signal.** There is no way to ask "is there a newer one?" short of watching the default branch.
- **Go is the sharpest case.** `go get` on a module with no tag resolves to a pseudo-version derived from the commit, which works but makes the dependency unreadable in `go.mod`.

## Suggested direction

Tagging costs almost nothing and fixes most of this even before publication. `v0.0.1` on the current commit of each repository would make the README's own instruction true, give consumers a name to pin, and make the next change visibly a new version.

Publishing to the registries is the larger step and can follow. `spec/sources.aon` in likeness already carries a `published` flag per language target so that switching from a sha to a version range is an edit rather than a redesign.
