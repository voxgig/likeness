# Paging: off by default, blind to `has_more`, and reachable only through `client._paging`

Filed from [voxgig/likeness](https://github.com/voxgig/likeness), which builds one application in five languages against SDKs generated by sdkgen and holds the ports to byte-identical output.

Three separate gaps, in increasing order of how wrong the answer gets.

## 1. The feature ships inactive

`Config.ts` generates `paging: { options: { active: false, … } }`. A consumer reading the generated feature list sees `paging` and reasonably assumes list operations paginate. Nothing does until it is switched on, and nothing says so at the call site.

## 2. Active, it never sees Joplin's own flag — and reports the opposite

`PagingFeature` reads body-level signals at `ts/src/feature/paging/PagingFeature.ts:131-136`:

```ts
if (null != body.next)       { paging.next = paging.next || body.next }
if (null != body.cursor)     { paging.cursor = body.cursor }
if (null != body.nextCursor) { paging.cursor = body.nextCursor }
if ('boolean' === typeof body.hasMore) { paging.hasMore = body.hasMore; explicitMore = true }
```

`hasMore`, never `has_more`. **Joplin's API definition — the one sdkgen consumed to generate this client — declares `has_more`**, in three response schemas in `.sdk/def/joplin-notes-folders-tags.json`.

So for this source the flag is invisible, `explicitMore` stays false, and with no cursor or `Link` header either, the inferred answer is `hasMore: false`. That is the failure mode that matters: not "no signal", but **a confident wrong one**. A consumer that trusted it would stop after page one and report the list complete.

Snake-case paging flags are not unusual — `has_more`, `next_cursor`, `next_page` are all common — and none of them are recognised.

## 3. What it computes is reachable only through an undocumented private field

```
rows: 2
sdk._paging: {"last":{"hasMore":false}}
ctrl after: {}
```

- `entity.list(reqmatch, ctrl)` returns a plain array; the result object is not exposed.
- `ctrl` is an input — the per-call cursor goes *in* that way — and is never written back.
- The signal lands at `client._paging.last` (`PagingFeature.ts:153`), an underscore-prefixed field on the **shared client**, holding only the most recent call. Two lists in flight overwrite each other, and nothing in the generated API documents it.

`py-data` already consumes it, via `getattr(client, "_paging")` in `py-data/pkg/fetch.py:147-152` — so one target has auto-iteration built on a private field that every other target's users would have to discover by reading the template.

## Reproduction

No credentials, no network.

```js
import pkg from '@voxgig-sdk/joplin'
const SDK = pkg.JoplinSDK ?? pkg.default ?? pkg
const seed = { entity: { note: { n1: { id: 'n1' }, n2: { id: 'n2' } } } }

// Default: the feature is inactive, nothing is recorded.
const off = SDK.test(seed)
await off.Note().list({})
console.log('inactive  ->', JSON.stringify(off._paging))   // undefined

// Active: recorded, but only on the client, and only the last call.
const on = SDK.test(seed, { feature: { paging: { active: true } } })
const ctrl = {}
await on.Note().list({}, ctrl)
console.log('active    ->', JSON.stringify(on._paging))    // {"last":{"hasMore":false}}
console.log('ctrl      ->', JSON.stringify(ctrl))          // {}
```

## Suggested fix, in order of value

1. **Recognise snake_case body flags** — `has_more`, `next_cursor`, `next_page` — or better, let the API definition declare which field carries the flag, since the definition already knows. This is the one that turns a wrong answer into a right one.
2. **Write the paging object back into `ctrl`.** It is already the parameter a caller passes and holds, it is per-call rather than per-client, and it needs no new API surface in any language.
3. **Document `client._paging`** if it is meant to be the interface, or make `py-data`'s use of it a supported accessor rather than a `getattr` on a private name.
4. Consider whether `active: false` is the right default for a feature whose absence silently truncates lists.

## What we do meanwhile

The adapter treats a page that came back at exactly the declared `page_max` as possibly-short, marks the answer `truncated` and names the instance in `meta.incomplete`. It over-reports rather than under-reports, which is the correct direction to be wrong in. Two transcript corpus entries pin it. The heuristic goes away when (1) is fixed.

## A correction to an earlier version of this report

An earlier draft said the signal was "computed and exposed nowhere a caller can reach". That was **wrong**: it was written after testing with the feature at its default `active: false`, and the absence of `client._paging` was read as absence of the mechanism rather than absence of the run. With the feature active the record does appear. The real problems are the three above, and the second one is worse than what was originally reported, not better.
