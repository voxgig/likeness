# `breaking --against` exits 0 whatever it concludes, so a CI gate has to parse prose

## What happens

```
$ aontu breaking --against schema.aon schema-v2.aon
verdict: breaking

$.note.&.extra: compat_required_added [compat]
  the general value requires this key; the specific value admits instances without it
  ...
$ echo $?
0
```

`verdict: breaking` and exit `0`.

## Why it matters

`vet` sets a careful and useful exit code vocabulary — 0 valid, 1 conflict, 3 incomplete, 4 the model does not stand up, 2 usage — and a gate can be written against it directly. `breaking` is the verb a release process most wants to gate on, and it is the one that cannot be gated without parsing output for the word `breaking`. That is fragile in exactly the place where fragility is expensive: a wording change quietly turns the gate off, and it fails open.

## Suggested direction

Give `breaking` the same treatment as `vet`: a non-zero exit when the verdict is `breaking`, and `--format json` so a CI annotator can read the findings structurally. If changing the exit code would break existing callers, a `--fail-on-breaking` flag would be enough.

## Impact on likeness

Our error code registry is a public interface — renaming a code is a breaking change — and `breaking --against` is how we intend to catch that in review. `PROCESS.md` currently has to tell contributors to read the verdict line rather than trust the exit status, which is the kind of instruction people follow until the day they are in a hurry.
