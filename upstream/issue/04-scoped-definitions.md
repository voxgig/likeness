# The API definitions are subsets narrow enough that no source can offer search

Not a defect — the definitions are deliberately scoped, and their names say so. This is a consumer reporting where the current scope stops, so that widening is driven by a real need rather than by guesswork.

## The surfaces as they stand

| SDK | Definition | Entities and operations |
|---|---|---|
| `joplin-sdk` | `joplin-notes-folders-tags` | `note`, `folder`, `tag` — full CRUD on each |
| `obsidian-sdk` | `obsidian-vault-only` | `vault` — create, list, load, update, patch, remove; `tag` — list only |
| `notion-sdk` | `notion-pages-databases-only` | `page`, `database` — create, load, update only |
| `linear-sdk` | `linear-issues-only` | `issue` — create, list, load, update; `team` — list, load |

## What that costs a consumer

**No source supports search**, because no definition includes a search operation. Joplin has `GET /search`, Notion has `POST /v1/search`, Linear has `issueSearch`, and Obsidian's plugin has `/search`. None is in scope. A cross-source search is the single most-wanted thing a tool over four notes applications can offer, and it currently cannot be built on these SDKs at all.

**Notion has no `list`.** Neither `page` nor `database` can be enumerated, so a Notion workspace cannot be walked. In the real API this is what `POST /v1/search` is for, which is also out of scope — so the two gaps compound.

**Notion has no `remove`, and Linear has no `remove`.** Both are defensible: Notion archives rather than deletes, and so does Linear. But it means a delete capability cannot be offered even where a user wants one.

**Obsidian has no `move` or `copy`.** These are OpenAPI 3.2 `additionalOperations`, absent from the model and from every generated client — out of contract rather than merely unimplemented.

## How we are handling it meanwhile

likeness declares all of the above as `false` in its capability matrix, refuses those operations before any network call, and has an automated check that the matrix matches the SDK's real operation surface, so a refusal can never quietly become a lie. Nothing is worked around; the capability is simply not offered.

## Suggested direction, in priority order

1. **Search, in all four.** It is the operation whose absence changes what can be built, rather than merely what can be done.
2. **`list` for Notion pages and databases** — otherwise a Notion connection is only usable if the user already knows the ids.

Happy to open one issue per operation in each repository if that is easier to schedule against; this one is a single place to see the shape of the gap.
