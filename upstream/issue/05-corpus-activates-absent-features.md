# The feature-behaviour corpus runs zero cases in every generated SDK

## What happens

The feature corpus has exactly one section:

```
$ cat .sdk/test/feature/feature-test-index.aon
# Feature behaviour cases, one section per feature.
feature: cost: @"./cost.aon"
```

Every case in it activates a `cost` feature:

```
$ grep -n "feature: \[" .sdk/test/feature/cost.aon | head -3
43:    feature: [ { name: 'cost', active: true, rates: { '#OP1': 0.25, '*': 0.01 } } ]
53:    feature: [ { name: 'cost', active: true, unit: 0.002 } ]
60:    feature: [ { name: 'cost', active: true, header: 'x-request-cost', perUnit: 0.5, unit: 99 } ]
```

One case also activates `netsim` as a feature (`cost.aon:87`).

No SDK generates either one. All four ship exactly eight features:

```
$ ls .sdk/model/feature/
debug.aon  feature-index.aon  idempotency.aon  metrics.aon
paging.aon  ratelimit.aon  retry.aon  test.aon  timeout.aon
```

The runner skips a case whose feature is absent — `ts/test/feature/Corpus.test.ts:264`, `if (!probe._rootctx.config.hasFeature(name)) { … skip }` — which is the right behaviour on its own. But since `cost` is the only section and it is absent everywhere, **the feature-behaviour corpus executes no cases at all, in any of the four SDKs, in any of the seven languages.**

The skip is by design and each case reports as skipped, so nothing is red. It simply is not testing anything.

## Why it matters

This corpus is the one worked example of a language-neutral feature-behaviour case: one declaration, run identically by seven generated ports. That pattern is exactly what likeness's own transcript corpus is modelled on, and we came here to read a working instance of it before writing ours. There isn't one that has run.

It also means any regression in the feature pipeline's *observable behaviour* — as opposed to its wiring — would not be caught by this corpus today, because the corpus never reaches a feature that exists.

## Suggested direction

Either would fix it, and the first is cheaper:

1. **Add a section for a feature that is generated.** `retry`, `ratelimit` and `timeout` all have observable behaviour that the `test` feature's `net:` option can drive deterministically — `failTimes` with `failStatus` is precisely a retry case. `idempotency` is another.
2. **Fail rather than skip when a corpus section names a feature no target generates**, at least under a strict flag. A corpus section that can never run in any target is a different thing from one that is inapplicable to a particular target, and only the tool can tell them apart.

Related: `netsim` appears in `cost.aon` as a feature name, but netsim is the `net:` option of the `test` feature rather than a feature of its own. That reference cannot ever match.
