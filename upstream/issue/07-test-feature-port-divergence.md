# The offline `test` feature behaves differently in each port, and in C and Ruby it cannot run the Linear SDK at all

The `test` feature is the seam every unit test in a multi-port application sits on. Its TypeScript implementation is the same 494 lines in all four SDKs, so there is one intended semantic — but the other ports implement different subsets of it, and the differences are behavioural rather than cosmetic.

## The one that stops work

**C and Ruby synthesise only a single-segment response envelope.** Every Linear operation unwraps a multi-segment one:

```
$ grep -h 'res: "`body' .sdk/model/entity/*.aon | sort -u
  res: "`body.data.issue`"
  res: "`body.data.issueCreate.issue`"
  res: "`body.data.issues.edges`"
  res: "`body.data.issueUpdate.issue`"
  res: "`body.data.team`"
  res: "`body.data.teams`"
```

Ruby matches `/\A`body\.([^`.]+)`\z/` — the character class excludes `.`, so a dotted path never matches (`rb/feature/test_feature.rb:9`).

C refuses explicitly (`c/feature/test.c:33-41`):

```c
// Exactly `body.<key>`; a deeper path is not an envelope this mock can
// synthesise, so it is left alone rather than guessed at.
if (0 == inner_len || NULL != memchr(spec + 6, '.', inner_len)) {
  return data;
}
```

So in the C and Ruby ports, **all six Linear operations return a payload the response transform cannot unwrap**. The offline test mode is not usable for the GraphQL SDK in those two languages. The comment shows the choice was deliberate for a single-segment case, but GraphQL makes multi-segment the normal case rather than an exotic one.

## The others, which are latent but not safe

| Behaviour | TS | Go | Py | Rb | C |
|---|---|---|---|---|---|
| `update` whose id matches nothing | **404** | 200, clobbers an arbitrary record | 200, clobbers the first | 200, clobbers the first | 200, clobbers the first |
| `update` merge depth | **deep** | shallow | shallow | shallow | shallow |
| stamp `id` on a seed record from its map key | yes | yes | yes | **no — dead code** | yes |
| point chosen when an entity has several | best: terminal `{id}`, else shallowest | same | **last** | **last** | **last** |
| required query params also matched | yes | yes | yes | **no** | **no** |
| multi-segment response envelope | yes | yes | yes | **no** | **no** |
| an op outside {load,list,create,update,remove} | returns undefined, no status | 404 | 404 | 404 | 404 |

The `update`-miss row is the worst of these. A test that updates a record the seed does not contain passes in four ports while silently corrupting an unrelated record, and fails cleanly in one. That is the failure mode a mock exists to prevent.

The Ruby id-stamping row means a Ruby seed record that relies on its map key to supply `id` is never matched, so the seeding idiom the READMEs show does not work there.

## Why it matters

[voxgig/likeness](https://github.com/voxgig/likeness) builds one application in five languages against these SDKs and holds the five to byte-identical output. Its unit tests run on this feature in every port, by design and on the reasoning that five hand-written mocks would disagree. These divergences put that disagreement back, one level down, where it is harder to see: a parity failure will look like a bug in the code under test.

## Suggested direction

The TypeScript implementation is the richest and is the natural canonical. In priority order:

1. **Multi-segment envelopes in C and Ruby**, without which GraphQL SDKs have no offline mode in those languages.
2. **Make `update` on a miss a 404 everywhere.** Silently clobbering a different record is worse than any error.
3. **Ruby's id stamping**, which makes the documented seeding idiom work.
4. The remaining rows — merge depth, point selection, query-param matching — as a pass to bring the five to one semantic.

A corpus case per row would keep them together afterwards. Related: the feature corpus currently runs zero cases in every SDK (`upstream/issue/05`), so there is nowhere these would be caught today.
